# GitHub / GitLab 連携

> **対象**: ボードのオーナー・管理者と、リポジトリに Webhook を登録する人
>
> - ボード設定でリポジトリを対応付け、GitHub / GitLab 側に Webhook を1つ登録するだけで使える
> - GitHub / GitLab の API は呼ばないので、アクセストークンや GitHub App は要らない
> - GitHub は環境変数の設定も不要。GitLab は使うインスタンスを `GITLAB_URLS` に書く

チケットへの紐付けの使い方(利用者向け)は [user-guide.md](../guide/user-guide.md#関連リンクブランチprコミット) を参照。

## できること

チケットに紐付けたプルリクエスト(GitLab ではマージリクエスト)について、次が自動で反映される。

- プルリクエストのタイトルと状態(オープン / ドラフト / マージ済み / クローズ)
- CI の結果(実行中 / 成功 / 失敗 / キャンセル)。GitHub は Actions など Checks を使う CI、GitLab は GitLab CI のパイプラインが対象
- ブランチ名の先頭にそのボードの表示IDがあるプルリクエストの自動紐付け(例: `feature/ABC-12`、`ABC-12-fix`)
- オプションで、マージによるチケットの自動完了と、CI の失敗・レビュー指摘でのエージェントへの自動差し戻し([連携のオプション](#連携のオプション))

## 事前の設定(運用者)

| 連携   | 環境変数                                                                                |
| ------ | --------------------------------------------------------------------------------------- |
| GitHub | 不要                                                                                    |
| GitLab | `GITLAB_URLS` に使うインスタンスの URL をカンマ区切りで書く(`setup-env` でも設定できる) |

- `GITLAB_URLS` の例: `GITLAB_URLS=https://gitlab.com,https://git.example.com/gitlab`。セルフホスト版はサブパスに置いたものも書ける。
  設定するとボード設定に「GitLab連携」が現れる
- Webhook のシークレット / トークンは `BETTER_AUTH_SECRET` で暗号化して保存する。**`BETTER_AUTH_SECRET` を変えた場合は、
  対応付けたすべてのリポジトリでシークレットの再発行(GitLab はトークンの設定し直し)が必要**
- GitHub / GitLab から Devuntu の URL(`BETTER_AUTH_URL`)へ HTTPS で到達できる必要がある

## GitHub の Webhook

シークレットはリポジトリごとに違うので、リポジトリごとに対応付けて、それぞれに Webhook を登録する。

1. ボード設定の「GitHub連携」でリポジトリ(`owner/name`。リポジトリの URL を貼ってもよい)を追加する。
   Webhook URL と Webhook シークレット、GitHub 側での登録手順が表示される(シークレットはこのときだけ表示される)
2. 表示された手順に従い、リポジトリの Settings → Webhooks で次のとおり登録する

| 項目         | 値                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------- |
| Payload URL  | 表示された Webhook URL(`<Devuntu の URL>/api/github/webhook/<ID>`)                        |
| Content type | `application/json`                                                                        |
| Secret       | 表示された Webhook シークレット                                                           |
| イベント     | Pull requests / Check suites / Check runs(自動差し戻しを使うなら Pull request reviews も) |

- 検証を通った Webhook が最後に届いた日時が一覧に出る。登録直後に GitHub が送る ping でも更新されるので、届いているか確認できる
- シークレットを控え忘れた・漏れた場合は「シークレットを再発行」で作り直し、GitHub 側の Secret も入れ直す。
  作り直しの影響はそのリポジトリの対応付けだけ
- 「シークレット未設定」と表示されたリポジトリは、「シークレットを再発行」で発行し、GitHub 側の Payload URL と Secret を登録し直す
- Organization の Webhook には対応していない(対応付けたリポジトリ以外のイベントは受け取っても捨てる)

## GitLab の Webhook

GitLab のトークンは Webhook ごとに違うので、プロジェクトごとに対応付けて、それぞれに Webhook を登録する。

1. ボード設定の「GitLab連携」でインスタンス(複数あるとき)と検証方式を選び、プロジェクトのパス
   (`group/subgroup/project`。プロジェクトの URL を貼ってもよい)を追加する。
   Webhook URL と GitLab 側での登録手順(シークレットトークン方式ならトークンも)が表示される
2. 表示された手順に従い、プロジェクトの Settings → Webhooks で、表示された Webhook URL(`<Devuntu の URL>/api/gitlab/webhook/<ID>`)を登録する。
   Trigger は Merge request events / Pipeline events を選ぶ(自動差し戻しを使うなら Comments も)
3. 検証方式に合わせてトークンを設定する

| 検証方式             | 対象               | 設定                                                                                                                |
| -------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 署名トークン(推奨)   | GitLab 19.0 以降   | GitLab 側で「Generate signing token」を押し、表示された `whsec_...` を devuntu の「署名トークンを設定」に貼り付ける |
| シークレットトークン | GitLab 19.0 より前 | devuntu が作って一度だけ表示するトークンを、GitLab 側の Secret token に貼り付ける。「トークンを再発行」で作り直せる |

- 使えるなら署名トークンにする。送信から5分を超えた配送は受け付けないので、サーバーの時刻がずれていると検証に失敗する。
  署名トークンを設定したプロジェクトは、シークレットトークンだけのリクエストを受け付けない
- トークンを設定するまで、そのプロジェクトの Webhook は受け付けない。検証を通った Webhook が最後に届いた日時が一覧に出るので、
  GitLab 側の「Test」で届くか確認できる
- プロジェクトのパスを変えた(改名・移動した)場合は、対応付けをやり直す(別のプロジェクトのイベントは受け取っても捨てる)
- グループ Webhook(Premium 以上)と Merged results pipeline(Premium 以上。マージ後のコミットで CI が走るため MR の head と一致しない)には対応していない

## 連携のオプション

ボード設定の各連携で、次の2つをオンにできる(GitHub / GitLab それぞれで設定する。設定できるのはボードのオーナーと管理者)。

- **「プルリクエストのマージでチケットを完了にする」/「マージリクエストのマージでチケットを完了にする」** —
  紐付いたプルリクエスト(マージリクエスト)がマージされると、チケットを自動的に完了にする
- **「CI失敗・レビュー指摘でエージェントへ自動差し戻しする」** — CI の失敗やレビュー指摘(CodeRabbit などのボットを含む)があると、
  AIエージェントが報告済みのチケットを自動で差し戻して直させる。使う場合は、Webhook のイベントにレビュー / コメントを追加する

自動差し戻しの動き:

- 1チケットあたりの回数には上限がある(1〜20回、既定3回)。回数はチケット詳細の処理状態の横に出る
- CodeRabbit のように push のたびに再レビューするボットでは、指摘が続くと上限まで差し戻しが続く。上限は小さめにしておく
- 数回に分けて届いた指摘は、最後の指摘から2分待ってまとめて1回の差し戻しにする
- 担当者を替えると回数は 0 に戻る

判定の細かい条件は [agent-runner-internals.md](../dev/agent-runner-internals.md#自動差し戻しci-の失敗レビュー指摘)(開発者向け)を参照。

## 詰まったときに見る場所

| 症状                                        | 確認すること                                                                                       |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 「最終受信」が更新されない                  | GitHub / GitLab 側の Webhook の配信履歴(Recent Deliveries)のステータス。Payload URL とシークレット |
| 配信履歴が 401                              | シークレット(トークン)が一致しているか。GitLab の署名トークンならサーバーの時刻のずれ              |
| 配信履歴が 404                              | Payload URL の ID が正しいか。ボード設定で対応付けを外していないか                                 |
| ボード設定に「GitLab連携」が出ない          | `GITLAB_URLS` を設定して `docker compose up -d` で作り直したか                                     |
| PR は紐付いたが CI の結果が出ない           | GitHub は Check suites / Check runs、GitLab は Pipeline events を Webhook のイベントに入れたか     |
| 自動差し戻しが動かない                      | ボード設定でオプションを有効にしたか。レビュー / コメントのイベントを Webhook に入れたか           |
| `BETTER_AUTH_SECRET` を変えたら受信できない | シークレットの再発行(GitLab はトークンの設定し直し)                                                |
