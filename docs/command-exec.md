# リモート実行

あらかじめ定義しておいた処理を画面のボタンから実行し、出力をリアルタイムで見る仕組み。
デプロイやバッチの再実行など、これまでサーバーへ SSH して手作業していた運用を画面へ寄せるためのもの。

既定では無効。`COMMAND_EXEC_ENABLED=true` と定義ファイルの配置の両方が揃って初めて動く
(環境変数の一覧は [environment-variables.md](environment-variables.md#リモート実行) を参照)。

利用者から見た使い方は [user-guide.md](user-guide.md#リモート実行) を参照。

## 全体の流れ

```
commands/*.yaml ──> /commands(実行できるコマンドの一覧)
                      │  選択して実行
                      ▼
              command_run を queued で作成 ──> ワーカーが掴む
                                                  │
                                                  ▼
                                        ssh <host> '<コマンド>'
                                                  │ 出力
                                                  ▼
                                        command_run_chunk へ保存
                                                  │
                      /commands/runs/[id] <──SSE──┘
```

実行は待ち行列に積まれ、ワーカーが順に処理する。押した瞬間に走るのではないのは、
リクエストの寿命と実行の寿命を切り離すため(長時間のジョブでもレスポンスを待たせず、
アプリの再起動にも耐えられる)。

**出力は必ず DB を経由して画面へ届く。** 実行しているプロセスと画面の接続を直接つながないので、
途中から見る・別のタブで見る・リロードする・終わってから履歴として見る、がすべて同じ経路になる。

## 定義ファイル

実行できる処理の定義そのもの。`COMMAND_DEF_DIR`(既定 `/app/config/commands`)の**直下**へ置く。
**接続先(`target`)は画面から作ることも変えることもできない。** 画面で管理するのは
ターゲットへのアサインだけで、`commands` の編集も `target.editable: true` を
書いたファイルに限られる([画面から編集する](#画面から編集する)を参照)。

- 対象はディレクトリ直下の `*.yaml` / `*.yml` のみ。サブディレクトリの中と、`.` で始まる名前は読まない
- **1 ファイルに 1 ターゲット。** そのファイルに書いたコマンドはすべてこのターゲットで動く
- ターゲットIDとコマンドIDは**ディレクトリ全体で一意**にする。重複した場合は、
  どちらを採っても実行履歴と実際に動く中身が食い違うため**関与したファイルをどちらも読み込まない**
- 上限はファイル 100 件、1 ファイルにつきコマンド 100 件、全体でコマンド 200 件

ファイルを追加・更新・削除すると数秒で自動的に読み直される(`/admin/commands` の再読み込みボタンで即時反映も可能)。
**読み込みに失敗したファイルは直前の内容を保持しない。** 修正するまで、そのファイルのコマンドは実行できない状態になる。
古い定義で動き続けると「直したつもりが反映されていない」ことに気付けないため。
巻き込む範囲はファイル単位で、他のファイルのコマンドは動き続ける。

```text
/app/config/commands/
├── web01.yaml
└── db01.yaml
```

```yaml
# web01.yaml
version: 1

target:
  id: web01
  label: Web サーバー
  host: web01.internal
  port: 22
  user: deploy
  identityFile: ops_ed25519
  editable: false

commands:
  - id: deploy-web
    label: Web デプロイ
    description: Web アプリを指定環境へデプロイする
    executable: /opt/bin/deploy.sh
    args: ['{{env}}', '{{verbose}}']
    inputs:
      - type: select
        key: env
        label: 環境
        options:
          - { value: staging, label: ステージング }
          - { value: production, label: 本番 }
      - type: checkbox
        key: verbose
        label: 詳細ログ
        whenTrue: ['--verbose']
    timeoutSec: 900
    requireConfirm: true
    confirmText: 本番環境へデプロイします。よろしいですか?
    requireFreshSession: true
    singleton: true
    sortOrder: 10
```

定義に無い項目を書くと読み込みエラーになる。綴りを間違えた設定が黙って無視され、
「書いたのに効かない」状態になるのを防ぐため。

### ターゲット

「どのホストへ、どのユーザーで、どの鍵で入るか」の組。同じホストでもユーザーや鍵が違えば
別のターゲットとして別のファイルに書く。第一階層が `host` ではなく `target` なのはこのため。

| 項目             | 必須 | 説明                                                                                     |
| ---------------- | ---- | ---------------------------------------------------------------------------------------- |
| `id`             | 〇   | 英数字で始まる 2〜64 文字。ディレクトリ全体で一意にする                                  |
| `label`          | 〇   | 画面に出す表示名。**ホスト名やユーザー名は画面に出さない**ので、ここだけが手がかりになる |
| `host`           | 〇   | 接続先のホスト名                                                                         |
| `port`           |      | 既定 22                                                                                  |
| `user`           | 〇   | 接続ユーザー                                                                             |
| `identityFile`   | 〇   | `COMMAND_SSH_DIR` 配下の**ファイル名**。パスやディレクトリ区切りは書けない               |
| `knownHostsFile` |      | 省略時は `COMMAND_SSH_KNOWN_HOSTS`                                                       |
| `editable`       |      | 既定 false。true にすると `commands` を画面から編集できる([後述](#画面から編集する))     |

### コマンド

| 項目                  | 必須 | 説明                                                                             |
| --------------------- | ---- | -------------------------------------------------------------------------------- |
| `id`                  | 〇   | 実行履歴にも残るキー。ディレクトリ全体で一意。後から変えると履歴と紐づかなくなる |
| `label`               | 〇   | 画面に出す名前                                                                   |
| `description`         |      | 画面に出す説明                                                                   |
| `executable`          | 〇   | 実行するファイル。絶対パス推奨                                                   |
| `args`                |      | 引数のテンプレート(後述)                                                         |
| `inputs`              |      | 入力項目(後述)                                                                   |
| `timeoutSec`          |      | 既定 900。5〜3600                                                                |
| `requireConfirm`      |      | 既定 true。実行前に確認ダイアログを出す                                          |
| `confirmText`         |      | 確認ダイアログの文言                                                             |
| `requireFreshSession` |      | 既定 false。true にすると、ログインから一定時間を過ぎている場合に再認証を求める  |
| `singleton`           |      | 既定 true。同じコマンドの同時実行を禁止する                                      |
| `sortOrder`           |      | 一覧での並び順                                                                   |

`requireConfirm` は**画面の歯止めであってセキュリティ境界ではない**(サーバーは確認の有無を知らない)。
取り返しのつかないコマンドには `requireFreshSession: true` を併せて指定する。

### 入力項目

**選択系だけで、フリー入力は無い。** 利用者が任意の文字列を渡せる経路を作らないための制約。

| `type`        | 展開のされ方                                                     |
| ------------- | ---------------------------------------------------------------- |
| `select`      | 選んだ値 1 個                                                    |
| `radio`       | 同上。選択肢が 2〜4 個で全部見せたいときに使う                   |
| `multiselect` | 選んだ値を**定義の `options` 順**で 0 個以上。選択順では並ばない |
| `checkbox`    | `whenTrue` / `whenFalse` に書いた配列をそのまま                  |

`select` / `radio` / `multiselect` の共通項目は `key` / `label` / `options`(`{ value, label }` の配列)。
`select` / `radio` は `defaultValue` と `required`、`multiselect` は `defaultValues` / `minSelected` / `maxSelected` を持つ。

### 引数の組み立て

`args` の要素が `{{key}}` と**完全に一致する**場合だけ、その入力項目の値へ置き換わる。

```yaml
args: ['{{env}}'] # OK
args: ['--flag={{env}}'] # NG: 定義の読み込み時に弾かれる
```

部分埋め込みを禁じているのは、値との境界が曖昧になるうえ、`multiselect` のような多値を
どう展開すべきか定義できないため。`--flag=production` のような形が必要なら、選択肢側に完成形を持たせる。

```yaml
inputs:
  - type: checkbox
    key: verbose
    label: 詳細ログ
    whenTrue: ['--flag=production']
```

引数に使える文字は `A-Z a-z 0-9 . _ : @ = / + , -` だけ。空白・引用符・`$`・バッククォート・
`;`・`|`・`&`・リダイレクト・括弧は書けない。**シェルのスクリプトを定義に埋め込むことはできない**ので、
複雑な処理はリモート側にスクリプトを置き、それを `executable` に指定する。

### 画面から編集する

`target.editable: true` を書いたファイルは、`/commands/targets/<ターゲットID>` から `commands` を
追加・編集・削除できる。編集はコマンド 1 件ぶんの YAML をその場で書く形で、保存時に
定義ファイルと同じスキーマで検証される。

検証は**書いている最中にも走る**。打鍵が止まると YAML の構文とスキーマの両方を見て、
問題のある行に印が付く(印にカーソルを合わせるか、行頭の印をタップすると理由が出る)。
まだ書かれていない必須項目は警告、書いた内容が間違っているものはエラーとして区別する。
保存はエラーが残っていても試せる。ファイルをまたぐID重複や編集権限のように、
サーバーでしか分からない問題は従来どおり保存時に返る。

**`target` はどのファイルでも画面から編集できない。** 接続先・ユーザー・鍵を画面から
増やせないということなので、この経路で広がる範囲は「既に鍵が通っているターゲットで、
その鍵のユーザーにできること」に閉じる。ここが編集を許してよいと判断した根拠になっている。

歯止めは 3 層ある。**どれか 1 つでも欠けていれば画面からは書けない。**

1. `COMMAND_DEF_DIR` が**書き込み可でマウントされている**(既定の構成では書けない)
2. そのファイルに `target.editable: true` がある(既定 false。書けるのはサーバーのファイルを置ける人だけ)
3. 操作しているのがそのターゲットの**オーナー**で、ログインから間もない
   (破壊的コマンドと同じ再認証を求める。オーナーは管理者がアサインで与える)。
   ログインからの経過時間は保存時だけでなく**編集を始める前**にも確かめる

書き込みを許すのは `config/commands` **だけ**にする。`config` 全体を書き込み可にすると
SSH の秘密鍵まで書き込み可になる。

```yaml
volumes:
  - type: bind
    source: ./config
    target: /app/config
    read_only: true
  # commands だけ書き込み可で重ねる。ssh(秘密鍵)は read-only のまま
  - type: bind
    source: ./config/commands
    target: /app/config/commands
```

知っておくべき挙動:

- **`commands` の中に書いたコメントは、画面から保存した時点で消える。** `target` 側の
  コメントと書式は残る。残したい説明は `description` へ書く
- 保存は**読み込んだ時点の内容と突き合わせて**行う。別の誰かが先にそのファイルを変えていた場合は
  保存されず、読み直してからやり直すことになる
- **ログインから時間が経っていると、追加・編集ボタンを押した時点で再認証を求められる。**
  認証後に元の画面へ戻ってから書き始める(書いてから弾かれて内容を失わないため)

## ターゲットのパターン

実行方式は SSH の一本に絞ってある。「どこで動かすか」は定義の書き方だけで決まり、アプリ側に分岐は無い。

| やりたいこと                       | 定義の書き方                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| リモートサーバーで実行             | 対象のターゲットごとに定義ファイルを作る                                                      |
| devuntu が載っているホスト側で実行 | `host` を `host.docker.internal` として登録し、ホスト側の sshd へ接続する                     |
| 別の Docker コンテナ内で実行       | `executable: /usr/bin/docker`、`args: ['exec', 'my-container', '/opt/bin/job.sh', '{{env}}']` |

ホスト側へ SSH する場合は、`compose.yaml` の devuntu サービスに
`extra_hosts: ['host.docker.internal:host-gateway']` を足す。
この構成はコンテナ分離を意図的に越えるので、後述の `command=` 制限を特に強く推奨する。

## SSHの準備

秘密鍵と known_hosts は `COMMAND_SSH_DIR`(既定 `/app/config/ssh`)へ read-only でマウントする。
**DB には保存しない。**

```sh
mkdir -p config/ssh && chmod 700 config/ssh
ssh-keygen -t ed25519 -N '' -f config/ssh/ops_ed25519 -C 'devuntu-command'
chmod 600 config/ssh/ops_ed25519

# 接続先のホスト鍵を取得する。登録が無いホストへは接続できない
ssh-keyscan -t ed25519 web01.internal > /tmp/web01.pub

# 取得した鍵のフィンガープリントを表示する
ssh-keygen -lf /tmp/web01.pub
```

`ssh-keyscan` は**接続先が本物かを検証しない**。取得の時点で経路に割り込まれていると、
攻撃者の鍵をそのまま固定してしまい、以降の `StrictHostKeyChecking=yes` はその誤った鍵を信頼し続ける。

表示されたフィンガープリントを、**SSH 以外の経路**(サーバーの管理コンソール、
クラウドのインスタンス作成ログ、構築担当者からの連絡など)で得た値と照合する。
一致したときだけ登録する。

```sh
cat /tmp/web01.pub >> config/ssh/known_hosts && rm /tmp/web01.pub
```

`compose.yaml` の devuntu サービスへ:

```yaml
volumes:
  - type: bind
    source: ./config
    target: /app/config
    read_only: true
```

接続は常に以下の指定で行う。**登録の無いホストへは接続できず、パスワードも尋ねない**(fail closed)。

```
-T -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes
-o UserKnownHostsFile=<known_hosts> -o GlobalKnownHostsFile=/dev/null
-o PasswordAuthentication=no -o KbdInteractiveAuthentication=no ...
```

パスフレーズ付きの鍵は使えない(`BatchMode=yes` のため)。代わりに次の `command=` 制限で守る。

### リモート側の堅牢化

リモートの `authorized_keys` で、この鍵にできることを 1 本のスクリプトへ縛る。
このスクリプトを**実行ゲート**と呼ぶ。

```
command="/opt/devuntu/bin/devuntu-gate.sh",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding ssh-ed25519 AAAA...
```

置き場やファイル名を変えたときは、`authorized_keys` の `command=` も合わせて書き換える
(既に運用しているホストでは、ここを直さない限り古いパスのまま起動され続ける)。

`command=` を付けると、ssh は要求されたコマンドを実行せず**必ずこのスクリプトを起動する**。
要求された内容は引数ではなく環境変数 `SSH_ORIGINAL_COMMAND` に入るので、
スクリプト側はそれを読んで実行する。

devuntu が送るのは `printf '<Sentinel>' >&2; exec '<実行ファイル>' '<引数>' ...` という 1 行で、
実行ファイルも引数もシングルクォートで包まれている(`command-args.ts` の `shellQuote`)。
引数に使える文字も `[A-Za-z0-9._:@=/+,-]` に限られている(`COMMAND_VALUE_PATTERN`)。

**`SSH_ORIGINAL_COMMAND` をそのままシェルへ渡してはいけない。** 許可済みの断片が含まれるかを
部分一致で確かめるだけでは、`rm -rf /; exec '/opt/devuntu/bin/deploy.sh'` のように
前後へ任意のシェル構文を足した要求が通ってしまう。`exec` 以降だけを取り出し、
**文字列ではなく引数の並びとして起動し直す**。

文字の検査は**通す文字を並べる**(許可リスト)。弾きたい文字を並べる形にすると、
改行のように目に見えない区切り文字を取りこぼしたときに、それがそのまま任意コマンドの実行になる。

実行ゲート(`devuntu-gate.sh`)を次の形にしておくと、許可外のコマンドを弾いたうえで、
**中断したときにリモート側のプロセスも確実に落ちる**。アプリは中断時にまず stdin を閉じるので、それが合図になる。

許可の単位は**ディレクトリ**にしてある。コマンドを増やすときは許可ディレクトリへスクリプトを置くだけで済み、
鍵の設定を書き換えなくてよい。

```sh
#!/bin/sh
# リモート実行の制限を行う実行ゲート

# -f: グロブ展開を止める(引数に * が残っていても展開させない)
set -euf

# 起動して良いディレクトリ。この直下に置いた実行ファイルだけを許可する。
ALLOW_DIR=/opt/devuntu/bin

# 引数に使って良い文字。先頭の一文字はシングルクォート。
# 弾きたい文字を並べるのではなく、通す文字だけを並べる(許可リスト)。
# 改行やタブは見た目に出ないうえ eval ではコマンドの区切りになるので、
# 列挙する側だと取りこぼしがそのまま任意コマンドの実行になる。
ALLOW_CHARS="'"' A-Za-z0-9._:@=/+,-'

deny() { echo "$1" >&2; exit 126; }

cmd=${SSH_ORIGINAL_COMMAND:-}

# 1. exec 以降だけを取り出す。
#    ここより前は捨てるので、前置きに何を書かれても実行されない。
rest=${cmd#*"; exec "}
[ "$rest" != "$cmd" ] || deny 'この鍵では許可されていない形式です'

# 2. devuntu が送る形に無い文字が 1 つでもあれば拒否する。
case "$rest" in
  *[!$ALLOW_CHARS]*) deny '引数に使えない文字が含まれています' ;;
esac

# 3. 残るのはシングルクォートと安全な文字だけ。引数の並びへ戻す($cmd は評価しない)
eval "set -- $rest"
[ "$#" -ge 1 ] || deny 'この鍵では許可されていない形式です'

# 4. 実行ファイルが許可ディレクトリの直下かを確かめる。
#    `..` は許可文字に含まれるため、前方一致だけではディレクトリの外へ抜けられる。
#    サブディレクトリも通さない(置いてあるものを一目で数え切れる状態に保つため)
case "$1" in
  *..*) deny 'この鍵では許可されていないコマンドです' ;;
  "$ALLOW_DIR"/*/*) deny 'この鍵では許可されていないコマンドです' ;;
  "$ALLOW_DIR"/?*) ;;
  *) deny 'この鍵では許可されていないコマンドです' ;;
esac

# 5. 起動したことをSentinelで知らせる。実行ゲートは `exec` より前を捨てるので、
#    devuntu が付けたSentinelはここまで届かない。これが無いと、コマンドが 255 で終わった場合に
#    ssh 自身の失敗(接続不可・認証失敗)と区別できなくなる
printf '\036devuntu-start\n' >&2

# 6. 中断の合図を受け取るため、この時点の stdin を fd 3 へ退避する。
#    `&` で動かすものは、ジョブ制御の無いシェル(ssh の command= はこれ)では
#    **明示のリダイレクトより前に stdin が /dev/null へ差し替えられる**(POSIX)。
#    退避しないと次の監視が起動直後に EOF を見て、正常なコマンドを即座に殺す(終了コード 143)
exec 3<&0

# setsid で別のプロセスグループにしておく。
# そうしないと後段の kill でグループごと落とせない。
# コマンド自身には stdin を渡さない(渡すと下の監視と読み合いになる)
setsid timeout -s TERM "${DEVUNTU_TIMEOUT:-3600}" "$@" </dev/null &
job=$!

# ssh が切れる / アプリが stdin を閉じると EOF になり、プロセスグループごと落とす。
# 待つのはビルトインの `read`。`cat` のような外部コマンドにすると、後段の kill で
# サブシェルだけが死んで読み手が残り、継承した stderr を掴んだまま ssh セッションが閉じなくなる
( while IFS= read -r _ <&3; do :; done; kill -TERM -"$job" 2>/dev/null ) &
watch=$!

rc=0
wait "$job" || rc=$?
kill "$watch" 2>/dev/null || true
exit "$rc"
```

`ALLOW_DIR` は実際の置き場に合わせること。例のまま `/opt/devuntu/bin` にしておくと、
別の場所に置いた `executable` は `deny` になり**終了コード 126** で失敗する。

`DEVUNTU_TIMEOUT` は**アプリからは渡らない**(ssh へ `SendEnv` を付けておらず、
子プロセスへ渡す環境変数も `PATH` / `HOME` / `LANG` に絞ってある)。リモート側で決める値なので、
`timeoutSec` の上限(3600)以上にしておき、打ち切りはアプリ側の `timeoutSec` に任せる。

この層で狭められるのは**何を起動できるか**まで。許可ディレクトリに置いた実行ファイルを、
許可した文字種の引数で動かせること自体は鍵を持つ相手に残る。
引数の値そのものを縛りたい場合は、スクリプト側でも受け取った値を検証する。

**そのディレクトリへ何を置けるかが、そのまま許可の範囲になる。** root 所有・他者書き込み不可にし、
外を指すシンボリックリンクを置かない(リンク先は `ALLOW_DIR` の判定を通り抜ける)。
もっと狭めたい場合は、`case` を個別のファイル名の列挙に替える。

**この実行ゲートを置かない場合**、中断してもリモート側に処理が残ることがある
(ローカルの ssh プロセスは必ず落ちる)。

**`target.editable: true` を使う場合、この `command=` 制限は必須とみなすこと。**
`executable` を画面から書けるということは、アプリの管理権限が
「このホストでこの鍵のユーザーができること全部」に届くということで、
起動できる実行ファイルの置き場を鍵側で限定しておかない限り歯止めがアプリの中だけになる。

## 権限

**許可の単位はターゲット。** コマンド単位の許可は持たない。分けたい相手が違うなら、
ターゲット(= 定義ファイル)を分ける。接続の実体がターゲットである以上、
守りたい境界も「どのホストへ入れるか」であって個々のコマンドではないため。

アサインは `/admin/commands`(リモート管理)で**管理者だけ**が設定する。
ユーザー単位とグループ単位の両方を指定でき、ユーザー単位にはロールが付く。

| ロール   | できること                                                           |
| -------- | -------------------------------------------------------------------- |
| `member` | そのターゲットのコマンドの実行                                       |
| `owner`  | 実行に加えて、コマンド定義の編集(`target.editable: true` のファイル) |

- **グループ経由のアサインはロールを持たず、常に `member` 相当。** オーナーにしたい相手は
  ユーザー単位でアサインする
- **アサインされていないターゲットは、管理者でも実行できない。** 管理者の特権はアサインの操作だけ。
  定義を置いただけでは誰も実行できない状態から始まる(fail closed)
- **アサインの操作はオーナーにも開かない。** 自分の権限を自分で増やせる経路を作らないため。
  ボードでは owner が参加者を足せるが、ここは接続先への到達可否そのものなので切り分けてある
- 定義から消えたターゲットにアサインが残っても、**権限は一切与えない**。判定は
  読み込み済みの定義に載っているターゲットだけを見る。残った行は `/admin/commands` に
  「定義に存在しないターゲット」として出るので、そこから消す(同じ ID で作り直したときに
  昔のアサインが復活するのを避けるため)

実行履歴は実行者本人と管理者だけが見られる。

## 安全性の考え方

SSH の exec は、リモートのログインシェルに 1 本の文字列を渡す仕様になっている。
そのため「配列で渡したから安全」はローカル側でしか成立しない。次の 4 層で防いでいる。

1. **選択肢の閉包** — 値は定義の `options` に含まれるものだけ。画面でもサーバーでも同じ関数で検証する
2. **文字集合** — 生成された引数を、使える文字だけかどうかで最終確認する
3. **クォート** — 全要素をシングルクォートで包む
4. **リモート側の縛り** — `authorized_keys` の `command=`(推奨)

加えて、子プロセスへ渡す環境変数は `PATH` / `HOME` / `LANG` だけに絞ってある
(DB の接続文字列などが子プロセスから見えないようにするため)。

### 画面から定義を編集できるようにすると何が変わるか

上の 4 層は「利用者が任意の文字列を実行させられないこと」を守っている。
`target.editable: true` を書いたファイルでは、**そのターゲットのオーナーに限り `executable` そのものを
画面から書ける**ようになるので、この前提がオーナーに対してだけ外れる。

つまり**オーナーのアカウントの侵害が、「そのターゲットの SSH 先での任意コード実行」へ昇格する。**
オーナーを与えるのは管理者だけなので、この昇格の範囲は管理者が選んだターゲットに閉じる。
曖昧にしておくと、後から読んだ人が「それなら `target` も編集できてよいはずだ」と考えてしまうので、
ここははっきり書いておく。

守れているのは次の 2 点で、これが編集を許してよいと判断した根拠になっている。

- **接続先が増えない。** `target`(ホスト・ユーザー・鍵)は画面から一切変えられないので、
  影響は「既に鍵が通っているターゲットで、その鍵のユーザーにできること」に閉じる
- **既定では機能そのものが動かない。** ディレクトリを書き込み可でマウントし、
  さらにファイルへ `editable: true` を書く、という 2 つの操作がどちらも
  サーバーのファイルを触れる人にしかできない

その先を縛るには、前述の[リモート側の堅牢化](#リモート側の堅牢化)で
**起動できる実行ファイルを許可ディレクトリの中だけに限る**。編集を有効にするならこれを併せて行うこと。

## 実行の記録

実行 1 件が `command_run`、出力が `command_run_chunk`。実行時点のコマンド名・接続先名・実行者名を
複写して持つので、定義が変わってもユーザーが削除されても履歴の意味は変わらない。

- 履歴は `/commands/runs` で見る。`/commands` の各カードにある時計のボタンから開くと
  `?commandKey=` が付き、そのコマンドの実行だけに絞り込まれた状態で開く(見える範囲は変わらない)
- **失敗しても自動では再試行しない。** 副作用のあるコマンドを勝手に再実行しないため
- アプリの再起動などで実行中のまま残った記録は、生存申告が途切れてから一定時間後に
  失敗(`interrupted`)として閉じられる
- 出力は 2MB を超えると保存を打ち切る(実行そのものは続く)。32MB を超えると暴走とみなして中断する
- 保持期間(`COMMAND_RUN_RETENTION_DAYS`)と件数の上限(`COMMAND_RUN_KEEP`)を超えた履歴は
  自動メンテナンスが消す([operations.md](operations.md#自動メンテナンス)を参照)

`failureKind` は失敗の分類。

| 値                 | 意味                                               |
| ------------------ | -------------------------------------------------- |
| `ssh_error`        | ssh 自身の失敗(接続不可・認証失敗・ホスト鍵不一致) |
| `connection_lost`  | 実行中に接続が切れた                               |
| `timeout`          | `timeoutSec` を超えた                              |
| `canceled`         | 画面から中断された                                 |
| `interrupted`      | 実行していたプロセスが応答しなくなった             |
| `output_limit`     | 出力が暴走した                                     |
| `start_failed`     | 鍵や定義の問題で起動できなかった                   |
| `log_write_failed` | ログを保存できなかった                             |

## 詰まったときに見る場所

| 症状                                                 | 見る場所                                                                                 |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| メニューに「リモート実行」が出ない                   | `COMMAND_EXEC_ENABLED` と、自分がターゲットにアサインされているか                        |
| `/admin/commands` に定義が出ない                     | 同画面のエラー表示。読み込めなかったファイルと原因が場所付きで出る                       |
| コマンドが一覧に出ない                               | そのターゲットにアサインされているか(`/admin/commands` でアサイン件数を確認)             |
| 追加したファイルが丸ごと出てこない                   | ターゲットIDかコマンドIDが他のファイルと重複していないか(重複すると両方とも落ちる)       |
| 「定義ディレクトリを読み込めない」                   | マウント漏れか、`COMMAND_DEF_DIR` がファイルを指している                                 |
| ターゲットが「未準備」                               | 鍵か known_hosts が読めていない。マウントとパーミッション(600)を確認                     |
| `ssh_error` で失敗する                               | ホスト鍵の登録、鍵の権限、リモートの `authorized_keys`                                   |
| 終了コード 127                                       | リモートに `executable` が無い。`ssh_error` ではないので接続自体は成功している           |
| 終了コード 126                                       | 実行ゲートの許可ディレクトリの外を指している。`ALLOW_DIR` と `executable` を突き合わせる |
| 開始直後に終了コード 143 で失敗し、理由の1行が出ない | 実行ゲートの中断監視が stdin を読めていない。`exec 3<&0` で退避しているか確認する        |
| ログが流れない                                       | リバースプロキシのバッファリング(nginx なら `proxy_buffering off;`)                      |
| 「既に実行中」で弾かれる                             | `singleton: true` のコマンドが動いている。履歴で状態を確認する                           |
| 定義の編集ボタンが出ない                             | 自分がそのターゲットのオーナーか。`target.editable` と書き込み可マウントも確認           |
| 保存が「他の人が編集しました」                       | 読み込んでから保存するまでに別経路でファイルが変わった。読み直してやり直す               |
| 「定義に存在しないターゲット」が出る                 | 定義から消えたターゲットにアサインが残っている。権限は無いが、同じIDで作り直す前に消す   |
